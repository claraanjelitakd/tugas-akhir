c:/study/tracerstudy/app/Services/Perusahaan/PerusahaanVerificationService.php
- Logika verifikasi perusahaan baru, modul auto-replace relasi alumni ke master terverifikasi, serta algoritma rekomendasi kemiripan cerdas (Multi-Level String Similarity Matching + Geographic Scoring) untuk mencegah data ganda:
  * Pembersihan teks: menghapus tanda kurung cabang `(...)`, normalisasi simbol/spasi, dan pemfilteran stop words unit/badan usaha.
  * Hierarki Pencocokan: Level 1 Identik (95 pt), Level 2 Akronim Penuh (88 pt), Level 3 Frasa Substring (75-90 pt), Level 3B Akronim Parsial/Compound (70-80 pt), Level 4 Irisan Kata Token Intersect dengan syarat rasio overlap >= 33% & proteksi sektor industri generik tunggal (50-75 pt), Level 5 Fuzzy Typo `similar_text` >= 60% (hingga 100 pt).
  * Pembobotan Geografis: Bonus +20 poin (Kabupaten/Kota sama) dan +10 poin (Provinsi sama).
  * Panduan lengkap dan simulasi kasus di docs/verifikasi-perusahaan-similarity.md.

c:/study/tracerstudy/app/Services/Export/AlumniTracerExcelExporter.php
- Service pembentukan berkas ekspor spreadsheet Microsoft Excel dan arsip ZIP multi-sheet untuk data rekap alumni, respon kuesioner tracer universitas, kuesioner evaluasi prodi, dan lembar evaluasi atasan langsung per prodi dan tahun kelulusan.

B. TANGGUNG JAWAB SETIAP KOMPONEN
----------------------------------------------------------------------------------------------------
1. `LinkedInSyncController`:
   - Menangani request HTTP dari UI Superadmin.
   - Mengambil data tahun kelulusan unik dari `data_akademik` / `yudisium`.
   - Mengirim data alumni, metrik KPI awal, dan data staging review ke frontend Inertia.
   - Endpoint JSON asinkron untuk `syncSingle($id)`, `syncBatch(Request)`, `approve($id)`, dan `reject($id)`.
   - Mengarahkan aksi approval untuk memperbarui `biodata` dan mendaftarkan `perusahaan` baru berstatus `Menunggu Verifikasi`.

1.b `LinkedinSyncResult` (Model Staging & Audit):
   - Menyimpan seluruh payload hasil scraping eksternal (`scraped_data`) secara terisolasi tanpa langsung mengubah master alumni.
   - Melacak siklus hidup persetujuan (`pending`, `approved`, `rejected`), waktu scraping, dan user reviewer (`reviewed_by`, `reviewed_at`).
   - Menyediakan data historis sinkronisasi untuk keperluan penelusuran audit universitas.

2. `LinkedInProfileService`:
   - Orkestrator proses bisnis sinkronisasi data alumni.
   - Mengisolasi transaksi basis data per-alumni (`DB::transaction`). Kegagalan satu alumni tidak membatalkan batch lainnya.
   - Mencatat jejak audit trail ke `LogActivity::record()` dengan aksi `linkedin_sync`.
   - Menangani skenario status: SUCCESS, NOT_FOUND, SKIPPED, dan ERROR.
   - Bergantung pada interface `LinkedInProfileProvider`, bukan class konkret.

3. `LinkedInProfileProvider` (Interface / Contract):
   - Mendefinisikan kontrak tunggal: `findByUsername(string $username): ?LinkedInProfile`.
   - Menjamin bahwa baik Mock maupun API eksternal wajib mengembalikan DTO `LinkedInProfile`.

4. `MockLinkedInProvider`:
   - Driver default untuk development dan pengujian lokal.
   - Memeriksa ketersediaan berkas Mock JSON di `storage/app/mock/linkedin/{username}.json`.
   - Jika berkas tidak ditemukan, menggunakan generator dinamis kontekstual dari data alumni lokal.
   - Mendukung skenario pengujian: 404 (diawali `notfound_`), empty username (`SKIPPED`), dan valid profile.

5. `ApiLinkedInProvider`:
   - Driver masa depan untuk integrasi API resmi server-to-server menggunakan API Key.
   - Menginjeksi `api_key` dan `api_base_url` dari Laravel config (`services.linkedin.*`).
   - Menggunakan HTTP Client Laravel (`Illuminate\Support\Facades\Http`).
   - Bertanggung jawab menormalisasi respons HTTP eksternal ke DTO `LinkedInProfile`.
   - Menormalisasi status HTTP error (401, 403, 404, 429, 500, timeout) ke internal exception tanpa membocorkan API key.

6. `LinkedInProfile` & `LinkedInPosition` (DTOs):
   - Objek transfer data yang memegang informasi profil resmi LinkedIn.
   - Agnostik database: tidak bergantung pada model Eloquent maupun tabel database.

7. `LinkedInProfileMapper`:
   - Menerapkan 4 aturan penentuan posisi kerja saat ini (Current Position).
   - Menjalankan pencocokan perusahaan eksak dan membuat record baru jika belum terdaftar.
   - Menjaga data otoritatif alumni agar tidak tertimpa.

8. Company Matching (`findOrCreateCompany`):
   - Melakukan exact matching nama perusahaan (case-insensitive & trimmed).
   - Jika perusahaan baru dibuat, status verifikasinya SELALU `Menunggu Verifikasi`.
   - Tidak melakukan fuzzy matching agresif atau menebak kabupaten/skala secara liar.

9. Activity Logging (`LogActivity::record`):
   - Mencatat seluruh aksi sinkronisasi (berhasil/gagal) dengan action `'linkedin_sync'`.
   - Menyimpan `old_values`, `new_values`, ringkasan perubahan, IP address, dan User Agent.
   - Dilarang keras menyimpan API key, token, atau kredensial rahasia di database log.

10. Driver Resolver (`AppServiceProvider`):
    - Satu-satunya titik pemutus provider dalam aplikasi berdasarkan nilai `LINKEDIN_DRIVER`.
    - Menggunakan statement `match(config('services.linkedin.driver', 'mock'))`.

C. ALUR DATA SINKRONISASI (DATA FLOW)
----------------------------------------------------------------------------------------------------
Alur eksekusi aktual saat Superadmin mengklik sinkronisasi pada UI:

1. [UI Superadmin] (Index.vue)
   Pengguna memilih Tahun Kelulusan -> Klik tombol [Sinkronkan] (Single) atau [Sinkronkan Tahun 2024] (Bulk).
   Frontend mengirim HTTP POST asinkron (fetch dengan header X-CSRF-TOKEN) tanpa full page reload.

2. [Controller] (LinkedInSyncController)
   Menerima request -> Mencari record Biodata -> Memanggil `LinkedInProfileService::syncBiodata()`.

3. [Service] (LinkedInProfileService)
   - Cek username: Jika kosong -> Langsung kembalikan status `SKIPPED`.
   - Memulai transaksi database per-alumni: `DB::beginTransaction()`.
   - Memanggil `LinkedInProfileProvider::findByUsername($username)`.

4. [Driver Resolver & Provider] (AppServiceProvider -> MockLinkedInProvider / ApiLinkedInProvider)
   - Jika `LINKEDIN_DRIVER=mock` -> `MockLinkedInProvider` membaca berkas JSON / generator dinamis.
   - Jika `LINKEDIN_DRIVER=api`  -> `ApiLinkedInProvider` memanggil HTTP client ke external API resmi.
   - Provider mengubah payload menjadi DTO `LinkedInProfile`.

5. [Mapper] (LinkedInProfileMapper)
   - Memilih posisi aktif (`endMonthYear == null`, start date terbaru).
   - Mencocokkan nama perusahaan di tabel `perusahaan` (jika baru: `status_verifikasi = Menunggu Verifikasi`).
   - Menyiapkan array pembaruan `posisi_jabatan` dan `perusahaan_id`.

6. [Database & Audit Trail]
   - Model `Biodata` diperbarui (`$biodata->update(...)`).
   - `LogActivity::record()` mencatat aksi sinkronisasi ke tabel `log_activities`.
   - `DB::commit()` mengunci perubahan. Jika terjadi error, `DB::rollBack()` dijalankan.

7. [UI Feedback]
   Controller mengembalikan JSON -> Baris tabel di frontend berubah status secara instan (Berhasil/Gagal)
   beserta data perusahaan/jabatan baru tanpa memuat ulang halaman browser.

D. ALUR PEMILIHAN PROVIDER (ENV SWITCH)
----------------------------------------------------------------------------------------------------
Pemilihan provider dikendalikan sepenuhnya melalui variabel `LINKEDIN_DRIVER` pada berkas `.env`:

1. Mode Mock (Default):
   ```env
   LINKEDIN_DRIVER=mock
   LINKEDIN_MOCK_PATH=storage/app/mock/linkedin
   ```
   -> Container me-resolve `MockLinkedInProvider`.
   -> Membaca berkas `storage/app/mock/linkedin/{username}.json` atau generator dinamis lokal.
   -> Tidak ada koneksi jaringan internet yang dilakukan.

2. Mode API (Masa Depan):
   ```env
   LINKEDIN_DRIVER=api
   LINKEDIN_API_BASE_URL=https://api.linkedin.com/v2
   LINKEDIN_API_KEY=rahasia_api_key_server_to_server
   ```
   -> Container me-resolve `ApiLinkedInProvider`.
   -> Menghubungi endpoint resmi server-to-server dengan otorisasi Bearer token.
   -> Membaca data riil LinkedIn.

E. BATAS TANGGUNG JAWAB MOCK DAN API
----------------------------------------------------------------------------------------------------
- Kedua provider mengimplementasikan interface yang sama: `LinkedInProfileProvider`.
- Keduanya wajib mengembalikan objek DTO yang sama: `LinkedInProfile` (berisi koleksi `LinkedInPosition`).
- Lapisan service (`LinkedInProfileService`) dan mapper (`LinkedInProfileMapper`) bersifat murni agnostik
  dan tidak pernah mengetahui apakah data berasal dari berkas JSON lokal atau HTTP response API.
- Format eksternal diselesaikan di level provider masing-masing melalui normalisasi DTO.

G. ATURAN PENCOCOKAN PERUSAHAAN (COMPANY MATCHING)
----------------------------------------------------------------------------------------------------
1. Pemilihan Posisi Aktif (Current Position):
   - Prioritas 1: Posisi dengan `endMonthYear == null` (posisi yang sedang berlangsung).
   - Prioritas 2: Jika >1 posisi aktif, pilih posisi dengan `startMonthYear` paling baru.
   - Prioritas 3: Jika tidak ada posisi aktif, pilih riwayat posisi dengan `endMonthYear` paling baru.
   - Prioritas 4: Jika tidak ada riwayat posisi, kembalikan null (posisi dan perusahaan alumni tidak diubah).

2. Aturan Pencarian & Pembuatan Perusahaan:
   - Pencarian awal: Exact match nama perusahaan case-insensitive & trimmed:
     `SELECT id FROM perusahaan WHERE LOWER(TRIM(nama_perusahaan)) = ?`
   - Jika belum ada: Sistem otomatis membuat record baru di tabel `perusahaan`.
   - **Kebijakan Verifikasi Mutlak**: Meskipun seluruh data terisi lengkap (provinsi, negara, alamat,
     sektor, skala), kolom `status_verifikasi` perusahaan baru WAJIB bernilai `'Menunggu Verifikasi'`.
   - Jangan melakukan fuzzy matching agresif yang berisiko menggabungkan dua institusi berbeda.
   - Jangan mengasumsikan jumlah karyawan LinkedIn sebagai nilai `skala` perusahaan (Lokal/Nasional/Internasional).

----------------------------------------------------------------------------------------------------
H. PENANGANAN KESALAHAN (ERROR HANDLING)
----------------------------------------------------------------------------------------------------
Sistem menangani seluruh kondisi kegagalan secara terisolasi tanpa merusak data eksisting dan tanpa
menampilkan stack trace teknis kepada pengguna:

1. `Username Kosong`:
   - Status: `SKIPPED`.
   - Pesan: *"LinkedIn username belum tersedia."*
   - Tidak melakukan pemanggilan ke provider.

2. `Profil Tidak Ditemukan` (HTTP 404):
   - Melempar `LinkedInProfileNotFoundException`.
   - Transaksi alumni di-rollback.
   - Status UI: `Gagal` dengan pesan *"Profil tidak ditemukan."*
   - LogActivity mencatat kegagalan audit trail.

3. `Otorisasi Ditolak / Forbidden` (HTTP 401 / 403):
   - ApiLinkedInProvider mencatat pesan error ke log internal server.
   - Melempar `LinkedInSyncException` ("Otorisasi LinkedIn API ditolak oleh server eksternal.").
   - API key TIDAK PERNAH dibocorkan ke pesan antarmuka pengguna.

4. `Batas Kuota Terlampaui` (HTTP 429 - Rate Limit):
   - Melempar `LinkedInSyncException` ("Batas kuota request LinkedIn API terlampaui.").

5. `Server Error & Timeout` (HTTP 500 / Connection Timeout):
   - Melempar `LinkedInSyncException` dengan pesan ramah pengguna ("Koneksi terputus atau timeout.").

6. `Respons Tidak Valid / Bukan JSON`:
   - Melempar `LinkedInSyncException` ("Format respons dari LinkedIn API tidak valid.").

B. BAGAIMANA DATA OTOMATIS KETARIK? (3 LAPISAN OTOMASI)
----------------------------------------------------------------------------------------------------
1. Lapis 1: Dynamic Eloquent Accessors (`app/Models/Biodata.php`)

2. Tahap 2: Mahasiswa Menyelesaikan Skripsi & Dinyatakan Lulus di Yudisium

     a) Update status kelulusan di `data_akademik`: `status_mahasiswa = 'L'`, tanggal lulus resmi,
        tahun lulus resmi (misal: 2026), dan semester akademik kelulusan.

15. ARSITEKTUR VERIFIKASI PERUSAHAAN (MULTI-LEVEL SIMILARITY & TEXT CLEANING PIPELINE)
====================================================================================================
A. LATAR BELAKANG & TANTANGAN DATA GANDA
Ketika alumni mengisi kuesioner atau memperbarui profil, mereka seringkali menuliskan nama instansi/perusahaan
tempat kerja dengan berbagai variasi penulisan, misalnya:
- "PT Bank Central Asia Tbk (Kantor Pusat)" vs "PT BCA INDONESIA" vs "Bank Central Asia"
- "Gojek" vs "PT Gojek Indonesia" vs "Gojek Super App"
- "Tokopedia" vs "PT. Tokopedia"
Tanpa sistem pembersihan dan pencocokan cerdas, basis data akan dipenuhi duplikasi perusahaan yang merusak
validitas statistik penyerapan alumni dan kerja sama mitra kampus.

B. ARSITEKTUR KOMPONEN
1. Domain Service: `app/Services/Perusahaan/PerusahaanVerificationService.php`
2. Controllers:
   - Super Admin : `app/Http/Controllers/SuperAdmin/Perusahaan/VerifikasiPerusahaanSuperAdminController.php`
   - Admin Fakultas: `app/Http/Controllers/AdminFakultas/VerifikasiPerusahaan/VerifikasiPerusahaanFakultasController.php`
   - Admin Prodi  : `app/Http/Controllers/AdminProdi/VerifikasiPerusahaan/VerifikasiPerusahaanProdiController.php`
3. Dokumentasi Teknis Rinci: `docs/verifikasi-perusahaan-similarity.md`

C. PIPELINE PEMBERSIHAN TEKS (TEXT PREPROCESSING PIPELINE - `cleanCompanyName`)
Sebelum dua nama perusahaan dibandingkan, string mentah disterilkan melalui tahapan:
1. Pemotongan Teks Keterangan Cabang/Lokasi dalam Tanda Kurung `(...)`:
   Regex `preg_replace('/\([^)]*\)/', ' ', $name)` memotong teks seperti `(Kantor Pusat)`, `(Surabaya)`, `(Persero)`
   sehingga perbandingan fokus pada entitas pokok badan usaha.
2. Normalisasi Karakter & Tanda Baca:
   Mengubah string ke huruf kecil (`strtolower`) dan menghapus simbol/tanda baca (`[.,\-_()\[\]\/\\\&+]`).
3. Penyaringan Stop Words Bertingkat:
   - Badan Usaha: 'pt', 'cv', 'tbk', 'persero', 'corp', 'inc', 'ltd', 'llc', 'yayasan', 'ud', 'koperasi', dll.
   - Unit/Cabang/Wilayah: 'kantor', 'pusat', 'cabang', 'kcu', 'kc', 'kcp', 'unit', 'witel', 'regional',
     'wilayah', 'area', 'divisi', 'office', 'hq', 'head', 'representative'.
   - Lembaga: 'dinas', 'kementerian', 'badan', 'lembaga'.
   - Geografis & Preposisi: 'indonesia', 'dan', 'and', 'of', 'the', 'in', 'di'.

D. HIERARKI PENILAIAN NAMA MULTI-LEVEL (MULTI-LEVEL NAME MATCHING)
Penilaian kemiripan nama menggunakan struktur hierarki prioritas:
1. Level 1 - Exact Match (Skor: 95 Poin):
   Nama bersih kedua entitas identik 100% setelah stop words dihilangkan.
2. Level 2 - Akronim / Singkatan Cocok (Skor: 88 Poin):
   Mencocokkan singkatan inisial huruf depan (`bca`) dengan nama panjangnya (`bank central asia`), atau sebaliknya.
3. Level 3 - Substring / Frasa Terkandung (Skor: 75 s/d 90 Poin):
   Salah satu nama bersih terkandung utuh di dalam nama lainnya (contoh: "Gojek" di dalam "Gojek Super App").
   Skor dasar 75 + bonus rasio panjang karakter (hingga 90 poin).
4. Level 3B - Akronim Parsial / Compound Acronym (Skor: 70 s/d 80 Poin):
   Salah satu kata token merupakan akronim dari entitas master (contoh: "BCA Digital" vs "Bank Central Asia").
5. Level 4 - Irisan Kata / Token Intersect (Skor: 50 s/d 75 Poin):
   Mencari kata-kata yang sama (`array_intersect`) dengan syarat:
   a) Rasio tumpang tindih kata minimal 33% (sepertiga bagian nama): `overlapRatio >= 0.33`.
   b) Bukan kecocokan tunggal pada kata sektor industri generik (`$genericIndustryWords`: 'bank',
      'universitas', 'sekolah', 'rs', 'hotel', 'studio', 'resto', 'cafe', 'toko', 'media', 'lab').
   Contoh: "CV Theresia Inovasi Mandiri" vs "Bank Mandiri" menghasilkan skor 58 (kata 'mandiri' spesifik),
   sedangkan "Bank Mandiri" vs "Bank Central Asia" menghasilkan skor 0 (kata 'bank' generik tunggal ditolak).
6. Level 5 - Fuzzy Distance / Deteksi Typo (Skor: 60 s/d 100 Poin):
   Menggunakan fungsi `similar_text()` (algoritma Ratcliff/Obershelp) jika persentase kemiripan huruf >= 60%.
   Contoh: "Bank Centrl Asia" vs "Bank Central Asia" menghasilkan skor 97%.

E. PEMBOBOTAN LOKASI GEOGRAFIS (GEOGRAPHIC LOCATION BONUS)
- Kabupaten/Kota Sama (`kabupaten_id` identik & skor nama >= 35): +20 Poin.
- Provinsi Sama (`propinsi_id` identik & skor nama >= 35): +10 Poin.
- Skor total dibatasi maksimal 100 poin.

F. MODUL AUTO-REPLACE & KONSOLIDASI DATABASE
Fitur `autoReplace()` mentransfer seluruh keterhubungan alumni (`biodata.perusahaan_id`) dari pengajuan
sementara ke entitas master terverifikasi, lalu menghapus data pengajuan yang tidak diperlukan, menjamin
integritas relasi tanpa menimbulkan data yatim (*orphaned records*).
